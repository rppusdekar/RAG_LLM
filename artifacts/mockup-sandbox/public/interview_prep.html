Q1   Walk me through how your CBOM scanner classifies quantum risk.

The scanner has two analysis layers. First, a static analysis engine — it walks every file in a codebase and runs regex patterns plus Python AST analysis to find cryptographic assets: algorithm names, library imports, key sizes, and cipher modes. It covers 40+ file types (Python, Java, JS, Go, C, YAML, config files, X.509 certs, TLS endpoints).

Once a finding is detected, it goes through a risk classifier with five levels:

  • VULNERABLE — broken by Shor's algorithm on a cryptographically relevant quantum computer: RSA, ECDSA, ECDH, classic DH, DSA (public-key crypto based on integer factorisation or discrete logarithm)
  • WEAKENED — security halved by Grover's algorithm (brute-force speedup): AES-128, SHA-256, HMAC-SHA1
  • SAFE — symmetric algorithms with sufficient key size to survive Grover: AES-256-GCM, SHA-384, SHA-512
  • PQC — NIST-standardised post-quantum algorithms: ML-KEM, ML-DSA, SLH-DSA
  • UNKNOWN — detected but not classified (e.g. custom or proprietary labels)

Key-size awareness is built in — RSA-1024 scores higher risk than RSA-2048, and both flag for CNSA 2.0 (which requires RSA ≥ 3072 until 2030, then drops RSA entirely). The final output is a CycloneDX 1.6 CBOM JSON plus a 0–100 risk scorecard with letter grade.

Q2   What's the difference between how Shor's and Grover's algorithms threaten classical cryptography?

Shor's algorithm is a quantum algorithm that solves integer factorisation and discrete logarithm problems in polynomial time. This completely breaks all public-key cryptography built on those hard problems — RSA, ECDSA, ECDH, DH. "Completely" means an attacker doesn't just need a bigger key; the algorithm itself is broken. These are labelled VULNERABLE in the scanner.

Grover's algorithm gives a quadratic speedup for brute-force search. For symmetric algorithms and hash functions, this effectively halves the security level — AES-128 becomes AES-64-equivalent, SHA-256 becomes SHA-128-equivalent. The fix is simply doubling the key size: AES-256 remains safe. These are labelled WEAKENED, not broken.

In plain terms: Shor makes public-key crypto obsolete — replace it. Grover makes short symmetric keys weaker — size up.

Q3   What is CNSA 2.0 and which algorithms does it mandate?

CNSA 2.0 (Commercial National Security Algorithm Suite 2.0) is the NSA's algorithm mandate for systems protecting US national security information. It sets hard deadlines for migration away from classical algorithms to PQC.

Mandated algorithms (post-migration):

  • Key encapsulation: ML-KEM (FIPS 203 / formerly CRYSTALS-Kyber) — minimum ML-KEM-1024 for NSS
  • Digital signatures: ML-DSA (FIPS 204 / formerly Dilithium) or SLH-DSA (FIPS 205 / SPHINCS+)
  • Symmetric: AES-256 (already in CNSA 1.0)
  • Hashing: SHA-384 / SHA-512

Key deadlines: Prefer PQC by 2025, plan for exclusively PQC by 2030, complete migration by 2033. RSA and ECC are disallowed after 2030 for new systems.

In my scanner, certs using RSA with validity extending past 2030 are flagged — that's a direct CNSA 2.0 compliance check.

Q4   What is CycloneDX and how does a CBOM differ from an SBOM?

CycloneDX is an OWASP-maintained open standard for describing software composition in machine-readable JSON or XML. It was originally designed for Software Bills of Materials (SBOMs) — listing every library, package, and dependency in a software system.

A CBOM (Cryptographic Bill of Materials) is an extension of that standard (formalised in CycloneDX 1.6) specifically for cryptographic assets. Where an SBOM answers "what software components does this system have?", a CBOM answers "what cryptographic algorithms, keys, protocols, and libraries does this system use — and are they quantum-safe?"

A CBOM entry describes: algorithm name, variant, key length, usage context (signing / encryption / hashing), the file it was found in, and its quantum risk classification. This is what regulators and auditors need for CNSA 2.0 compliance evidence.

My scanner outputs CycloneDX 1.6 CBOM JSON — the cryptoProperties component type — which is the format being adopted by US federal agencies for post-quantum migration reporting.

Q5   What is hybrid KEM and why is it used during the migration period?

A KEM (Key Encapsulation Mechanism) is how two parties establish a shared secret over an untrusted channel. Classical systems use X25519 (elliptic curve Diffie-Hellman). PQC systems use ML-KEM (Kyber).

Hybrid KEM runs both in parallel and combines their outputs. In my implementation (pqc_phase4/crypto/hybrid_kem.py):

  • Client generates an X25519 keypair AND an ML-KEM-768 keypair
  • Both public keys are sent to the server
  • Server encapsulates a secret using X25519 (classical) and ML-KEM (PQC)
  • The two shared secrets are combined using HKDF into one session key

Why hybrid during migration? Two reasons: (1) Safety hedge — if ML-KEM turns out to have an undiscovered vulnerability, X25519 still protects the session. If a quantum computer breaks X25519, ML-KEM still protects it. You need to break both simultaneously. (2) Backwards compatibility — systems that don't yet support ML-KEM can still negotiate via X25519. Hybrid lets you deploy PQC incrementally without a hard cutover.

This is the approach recommended by NIST and adopted by TLS 1.3 extensions (e.g. X25519Kyber768) now shipping in Chrome and Cloudflare.
